# Pair-selected launch flow with per-wallet protected buys

The launch form now discovers historically observed pair assets, verifies ERC-20 candidates against the factory, accepts a distinct protected-wallet buy per recipient, and adds a router-approval path for ERC-20 developer buys. The builder repeats ERC-20 pair membership before the wallet prompt, while native-only bundle buys still require a receipt and deployed curve code. But the client retains ERC-20 metadata from page render, the native funding display excludes one principal payment, and the new “automatic” wording masks per-row wallet sends. **Watch for:** **confirmed** ERC-20 decimal metadata is not re-read before an amount is encoded; **confirmed** the displayed native bundle total omits the developer buy; **confirmed** each purported automatic buy still waits for its own post-launch wallet signature.

**Verdict**: NEEDS_CHANGES

## High-level view

ERC-20 discovery correctly treats indexed history as a candidate source rather than an approval list. Its metadata is only read on the server render, while the signing path rechecks approval and economics but not the decimal scale used to encode user-entered amounts; native is also inserted as a supported pair without a native-specific verification read.

The wallet-row editor exposes a native bundle subtotal, but a native launch separately spends the developer buy and launch fee. The ERC-20 path checks allowance but not balance or a post-approval launch simulation, so it can consume approval gas before discovering an unfundable buy.

Refusing ERC-20 bundles before a newly deployed curve can receive an allowance is the right boundary. Native bundle buys remain individually signed transactions after receipt and chain reads, however, so they cannot honestly be presented as automatic or reliably launch-window protected.

<summary>Details</summary>

## High — ERC-20 amount units are not refreshed at signing — confirmed

`resolveVerifiedPairAssets` in `apps/web/src/app/launch/page.tsx` reads `decimals()` while rendering the server page. `LaunchForm.parseQuoteAmount` in `apps/web/src/app/launch/launch-form.tsx` converts developer-buy and protected-wallet inputs with that serialized value. At submit time, `buildLaunchTransaction` in `packages/pons/src/launch/builder.ts` rechecks `approvedPairTokens` and refreshes the economics digest, but neither it nor `submit` rereads ERC-20 metadata.

A page left open across a metadata upgrade or changed decimal implementation can encode a materially different raw amount from the one shown. The exact approval would approve that wrong raw amount. This contradicts the new `docs/WHITELIST_LAUNCH.md` requirement to read current ERC-20 metadata again before signing; re-read `decimals()`, compare it with the rendered asset, and force an amount review on change.

## High — The native bundle subtotal omits the opening buy — confirmed

`LaunchForm.bundleTotal` sums only `bundleRecipients`, while the “Total automatic buy” card says the connected wallet pays that amount plus the native launch fee and gas. For a native pair, `buildLaunchTransaction` sets `launch.value` to `launchFee + devBuyAmount`; the form defaults that omitted opening buy to 0.01 ETH. A 0.01 ETH protected buy therefore displays as 0.01 ETH plus fee and gas, while the launch also sends 0.01 ETH.

Show one pre-signing native requirement containing developer buy, bundle total, launch fee, and a gas allowance, then check the connected balance before the launch. The current summary can cause an unexpected spend or leave the post-launch bundle underfunded.

## High — “Automatic” protected buys still require one wallet signature per row — confirmed

The changed toggle in `LaunchForm` says “Automatically buy for these wallets after launch,” but `runBundle` awaits `walletClient.sendTransaction` for every planned buy. Those sends start only after the launch receipt, curve-code lookup, and curve-state reads. The revised disclosure removes the prior statement that the sequence is made of individual connected-wallet transactions and no longer interpolates the live `snipeTaxSeconds` value.

The flow cannot promise launch-window execution to a human signer, especially for multiple rows. `planBundle` already warns for longer sequential lists, but `LaunchForm` does not show those warnings. Describe this as a user-confirmed post-launch sequence with the live window and per-row send requirement, or use a batch, pre-authorized signer, or relay before calling it automatic.

## Medium — ERC-20 approval has no balance or post-approval launch preflight — confirmed

The ERC-20 branch in `LaunchForm.submit` calls `needsApproval`, which reads allowance, but never reads `balanceOf` or simulates the rebuilt `launchAndBuy` call after the approval receipt. As documented in `PONS-V2-BUNDLER.md`, the router pulls the developer buy with `safeTransferFrom`; approval can succeed with no balance, after which the launch reverts and the creator has already paid approval gas.

Check token balance before approval and simulate the refreshed launch after it. Keep the exact router approval, but block the second wallet request when the wallet cannot fund the declared developer buy.

## Low — Native ETH is labelled verified without a native verification read — confirmed

`resolveVerifiedPairAssets` unconditionally inserts `NATIVE_PAIR_TOKEN` and returns it as `native: true` without an approval, economics, or launch-feasibility read. `verifiedPairs.some((pair) => pair.native)` is therefore guaranteed true despite the error text saying the factory confirmed native ETH, and the form renders a “Verified live” badge. Skipping `approvedPairTokens(address(0))` is correct because that mapping is not the native mechanism; insertion is not factory verification.

Use a native-compatible feasibility read such as the configured `previewLaunchEconomics` path, or describe the option as protocol-native rather than live-verified. The builder preview remains the final signing-time gate.

## Low — The changed financial UI has no component-level coverage — confirmed

The added `packages/pons/src/launch/builder.test.ts` cases cover the factory mapping guard, and `packages/pons/src/trade/bundle.test.ts` verifies different recipient amounts. No located web test covers `LaunchForm` or `resolveVerifiedPairAssets`. Not tested: stale 6-decimal metadata before signing, aggregate native funding, insufficient ERC-20 balance after approval, pair switching, the disabled ERC-20 bundle state, and per-row wallet sends.

`pnpm --filter @stunks/pons test -- src/launch/builder.test.ts src/trade/bundle.test.ts` passed 49 tests, and `pnpm --filter @stunks/web typecheck` passed. Add route/form tests with a signing mock for the missing states.
